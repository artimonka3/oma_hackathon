# Промпт для организации задач ОМА в GitHub

Скопируйте текст ниже в GitHub Copilot с доступом к репозиторию и GitHub Projects. Приложите `OMA-product-spec.md`, `docs/technical-spec.md` и `README.md`. Старые концепции можно приложить как справочный материал.

При возможности заранее заполните:

- Репозиторий: `<owner/repository>` или текущий репозиторий Copilot.
- GitHub Project: `<ссылка на существующий Project>`; если его нет — создать у указанного владельца.
- Команда: `<GitHub login → роль/зона ответственности>`; если неизвестно, оставить исполнителей неназначенными и указать требуемую роль.
- Текущая организационная задача: `<номер или ссылка>`, если нужно связать с ней результат.

---

Ты отвечаешь за планирование реализации проекта «ОМА — от первой идеи до готового ремонта» и настройку GitHub Issues + GitHub Projects. Работай через доступные GitHub-инструменты, API или gh CLI.

Нужно фактически создать и связать Issues, добавить их в Project, заполнить поля и настроить доступные представления. Текстовый список предложений сам по себе не считается выполнением. Код продукта в этой задаче не реализуй.

## 1 Источники и сохранение решений

Сначала прочитай приложенные документы и текущее содержимое репозитория:

1. `OMA-product-spec.md` — согласованные требования и продуктовые решения.
2. `docs/technical-spec.md` — архитектура, данные, состояния, API и критерии проверки.
3. `README.md` — навигация по проекту.

Ранние `OMA-ar-concept.md` и `OMA-prorab-concept.md` — справочный брейншторм. При противоречиях используй основную спецификацию. Сопоставь документы с уже существующим кодом и задачами: не создавай повторную задачу на действительно завершённую работу, но и не считай наличие документа реализацией функции.

Архитектура уже выбрана. Организуй её реализацию; изменения концепции оформляй только как отдельные предложения с причиной, не применяй их молча.

Обязательно сохрани:

- Два пользовательских сервиса — ОМА.Собери и ОМА.Прораб — используют один проект ремонта.
- Комната и квартира с несколькими помещениями поддерживаются моделью данных.
- Backend на Go: два выделенных доменных модуля, общий кабинет, PostgreSQL и отдельный HTTP API симулятора ОМА.
- Каталог, поиск, история покупок, корзина, котировка, оплата и доставка ОМА в первой версии симулируются. Взаимодействие идёт через адаптер API.
- Собери: персонализация, варианты, закреплённые ограничения, имеющееся, визуализация/AR, спецификация и связанная корзина.
- Прораб: подбор, подготовленная проверка перед оплатой, согласование работ, отчёты, изменения и сопровождение до приёмки.
- Прораб получает один подготовленный адресный запрос; каждое изменение дизайна не отправляется ему заново.
- Работу принимает заказчик; ОМА помогает как посредник. AI не принимает этапы и не гарантирует качество по фотографии.
- История покупок не равна текущему остатку: имеющееся подтверждает пользователь.
- Базовая бизнес-модель — программное решение для ОМА ради дополнительных продаж и удержания. Обязательная комиссия с ремонта и подписки в scope не входят.
- Визуальный результат сопровождает клиента при выборе, покупке и ремонте.

Не сокращай MVP до одного AR-конструктора: первый сквозной результат должен включать оба сервиса и приёмку. В рамках демо ограничь число товаров, профилей и показываемых этапов, сохранив целостность.

## 2 Проверка контекста и доступов

Определи текущий репозиторий, владельца Project и права на Issues/Projects. Прочитай существующие открытые и закрытые Issues, Project items, поля, представления, labels и назначенных участников с пагинацией.

Если репозиторий или владелец Project неоднозначны, задай один короткий вопрос до создания данных. Подходящий существующий Project переиспользуй. Без заданных логинов не угадывай исполнителей: укажи требуемую роль и оставь Assignee пустым. Не назначай Copilot coding agent автоматически.

Проверь реальные возможности доступных инструментов и API. При необходимости используй gh REST/GraphQL вместо ограниченного инструмента. Не выдумывай выполненные действия. Если операция недоступна, выполни остальные независимые действия и сообщи точное ограничение. Не запрашивай секреты в сообщении.

## 3 Декомпозиция

Создай иерархию Epic → атомарные задачи. Feature используй только там, где это полезный промежуточный результат. Небольшие шаги оставляй чек-листом внутри Issue. Не создавай одинаковую работу одновременно в Epic, Feature и Task.

Epic — контейнер результата; исполняемая задача должна иметь одного ответственного, ясные входы и проверяемый результат. Ориентир размера — несколько часов или 1–2 рабочих дня одного человека; оценки предварительные. Крупные задачи раздели по смыслу, а не на пустые карточки отдельных файлов.

Покрой следующие области, сгруппировав их в разумное число Epic:

1. Контракты и основа: структура Go, среда разработки, PostgreSQL, миграции, сессии/роли, CI и общие ошибки API.
2. Проект: помещения, захваты, медиа, участники, версии, доступ и сохранённое состояние.
3. Mock OMA и адаптер: каталог/поиск, параметры, история, корзины, котировки, оплата-симуляция, заказы и доставка.
4. Собери и AI: бриф, предпочтения, ограничения, варианты, правки, сохранённые задания, валидация результатов и demo/live.
5. Визуализация: фото/3D, проверка устройств, AR, масштаб, переход между устройствами и резервный режим; способ захвата помещений.
6. Имеющееся и расчёт: подтверждение остатков, выделение между проектами, правила категорий, спецификация и распределение по комнатам.
7. Связь с магазином: синхронизация проектных строк, изменения из поиска/корзины, версии и согласованность состава.
8. Прораб до оплаты: профили/портфолио, подбор, preflight, адресная проверка, предложенные правки, действительность подтверждения и назначение.
9. Оформление: замороженная котировка, серверная авторизация, идемпотентность, события магазина и восстановление связи с заказом.
10. Исполнение: план, готовность материалов, фотоотчёты, замечания, приёмка, изменения и прогресс.
11. Посредничество: обращения, относящиеся документы, предложения ОМА, согласия и исход урегулирования.
12. Общий кабинет: визуальный ориентир, SSE, нужные действия, история, завершение, фактические остатки и следующий проект.
13. Сквозная проверка и показ: тестовые данные, роли демо, сценарии сбоев, интеграционные проверки, демонстрация и инструкции.

Это перечень покрытия, а не требование создать ровно 13 Epic. Следуй последовательности A–K технического приложения, учитывай реальные зависимости и возможности независимой работы.

Не создавай искусственные задачи на реальные платежи, собственное мобильное приложение, такси, обязательную комиссию и новую микросервисную архитектуру. Нерешённые вопросы провайдера AI или устройства для AR оформи ограниченными Research-задачами с конкретным результатом.

## 4 Содержание исполняемой Issue

Название формулируй как проверяемый результат. Все описания — на русском; технические идентификаторы сохраняй как в спецификации.

Шаблон:

### Цель
Какой результат появится и кому он нужен.

### Контекст
Связь с пользовательским сценарием и модулем.

### Что сделать
Конкретные действия и границы ответственности. Укажи необходимые контракты, экран или изменение данных, где применимо.

### Критерии готовности
Чек-лист наблюдаемого поведения: основной сценарий, существенные ошибки, права и согласованность данных. Подходящие тесты добавляются вместе с поведением; для простой документационной задачи не требуй бессмысленных программных тестов.

### Зависимости
Blocked by и связанные Issues с настоящими номерами/ссылками после создания. Укажи входной результат, который нужен от блокера.

### Ответственность
Основная роль, зона реализации и проверяющий по правилам команды, если задан.

### Источник
Файл и раздел спецификации; реальные ссылки на документы в репозитории, если они доступны. Для приложенных, но не опубликованных файлов укажи название и раздел без выдуманного URL.

### За пределами задачи
Только существенные соседние работы, если это помогает избежать дублирования.

В каждой Issue добавь стабильный служебный ключ в HTML-комментарии, например `<!-- oma-plan:key=checkout-authorize -->`. Одинаковая смысловая задача должна сохранять ключ между запусками.

Для Epic достаточно цели, границ, общего результата и ссылок на дочерние Issues. Не копируй туда весь текст каждой задачи.

## 5 Особо важные критерии покрытия

Проверь, что в задачах явно отражены:

- история покупки не уменьшает закупку до подтверждения текущего остатка;
- одну партию нельзя выделить сверх доступного объёма между проектами;
- повтор cart-sync не удваивает позиции и не удаляет посторонние товары;
- существенная замена материала делает проверку неактуальной; изменение только цены требует согласия с суммой, но не повторной технической проверки;
- готовые правки прораба принимаются для точной предложенной версии;
- основание для оплаты проверяется сервером магазина;
- повтор или потеря события не создаёт дубли и позволяет восстановить заказ;
- частичная доставка влияет только на обеспеченные этапы;
- работа со своими материалами не требует фиктивной покупки;
- отчёт прораба не увеличивает принятый процент до решения клиента;
- замечания, новые отчёты и приёмка сохраняют версии;
- посредник не принимает этап вместо клиента;
- изменение после оплаты не переписывает старый заказ;
- SSE и обновление страницы восстанавливают согласованное состояние;
- неправильный AI-ответ не снимает ограничения и не добавляет неизвестные товары;
- AR имеет честный резервный режим и проверенный масштаб;
- демонстрационные данные явно обозначены.

## 6 Поля Project

Создай или аккуратно переиспользуй:

- Status: Backlog, Ready, In Progress, Review, Done.
- Priority: High, Medium, Low.
- Work type: Epic, Feature, Task, Bug, Research.
- Area: Frontend, Backend, AI, 3D/AR, Integrations, QA, DevOps, Documentation, Product/UX.
- Scope: MVP, Next.
- Phase: этапы A–K из технической спецификации.
- Assignees: штатное поле исполнителей Issue, без дублирующего текстового поля.

Если штатный Type или существующее поле уже покрывает классификацию, используй его либо отдельный Work type, не меняя глобальные типы организации. Существующие ручные значения и полезные опции не удаляй.

Iteration, Start date, Target date и оценки добавляй только при наличии соответствующих данных или явной пользы. Не выдумывай даты и дедлайны. Согласованный объём продукта и минимальный связный демосценарий используй для Scope; расширения оформляй отдельно.

Labels используй для фильтрации в репозитории; переиспользуй близкие существующие значения. Не размножай одинаковые классификации без необходимости.

## 7 Иерархия зависимости и порядок

Используй настоящие parent/sub-issues и blocked-by/blocking, если доступны. Родительский Epic не является автоматическим блокером ребёнка. Если инструменты не позволяют создать связь, добавь взаимные ссылки и явно отметь fallback.

Сначала создай/найди Issues и собери карту ключ → номер → URL, затем установи ссылки и зависимости. Проверь отсутствие циклов и несуществующих номеров.

Выдели критический путь к первой сквозной демонстрации. Начальные задачи без незакрытых блокеров и с достаточными вводными помести в Ready; остальные — в Backlog. Высокий приоритет не означает готовность к старту.

Не делай каждый следующий Epic полностью зависимым от предыдущего: после согласования контрактов интерфейс, симулятор, расчёт и доменные модули могут разрабатываться независимо. Тесты поведения включай в соответствующие задачи; отдельные задачи оставь для действительно сквозных сценариев и контракта интеграции.

## 8 Представления и рабочие правила

Настрой доступными средствами:

1. Board — группировка по Status, обычная ежедневная работа.
2. Planning — таблица с Priority, Scope, Phase, Area, Work type и Assignees.
3. MVP — только Scope=MVP, с приоритетом и зависимостями.
4. Ready — атомарные готовые к старту задачи.
5. Blocked — незавершённые задачи с блокирующими связями.
6. Epics/Roadmap — крупные результаты по этапам; timeline используй при наличии настоящих дат, иначе представление этапов.

При известной команде добавь удобное представление назначений. Если создание конкретного view/автоматизации недоступно инструменту, сохрани выполненную работу и перечисли точные оставшиеся настройки интерфейса.

В README проекта опиши правила:

- Backlog → Ready: достаточные вводные и выполненные обязательные зависимости.
- Ready → In Progress: назначен исполнитель и работа начата.
- In Progress → Review: результат доступен для проверки и самопроверка выполнена.
- Review → Done: критерии выполнены, review пройден, нужные проверки успешны, результат в целевой ветке/окружении.
- WIP: ориентир 1–2 активные исполняемые задачи на человека; Epic не учитывается как дополнительная работа.
- Автор указывает проверяющего; в PR есть ссылка на Issue и способ проверки.

Автоматизации настраивай только в пределах возможностей и согласованных правил. Не закрывай существующие Issues и не отмечай реализацию завершённой из-за создания плана.

## 9 Повторный запуск и сохранность

Перед созданием каждой карточки ищи стабильный ключ и смысловой дубликат, включая закрытые Issues. Новые связи и поля добавляй к существующим подходящим объектам. Ручные описания, статусы и назначения сохраняй; генерируемую часть обновляй явно выделенным блоком.

Не удаляй и не переименовывай чужие задачи, Project или поля вне этой работы. Не создавай новый Project, если указан подходящий существующий. При частичном сбое продолжай по сохранённой карте созданных объектов и учитывай ограничения API.

Сохрани в репозитории либо подготовь как файл `docs/github-project-plan.md`: ссылку на Project, этапы, правила, карту Issues, роли, критический путь и оставшиеся ручные шаги. Не перезаписывай основной продуктовый документ. Если публикация файла требует отдельного процесса, сообщи об этом и предоставь содержимое; создание Issues и Project от этого не должно останавливаться.

## 10 Проверка и итоговый отчёт

После создания повторно прочитай фактические данные GitHub и проверь:

- задачи являются repository Issues и добавлены в нужный Project;
- каждая исполняемая задача имеет источник, критерии, приоритет, область, Scope и основную роль;
- заданные исполнители существуют и действительно назначены;
- родительские связи и зависимости сохранены; циклов нет;
- стартовый Ready не содержит заблокированных задач;
- значения Project действительно выставлены, а не только написаны в теле Issue;
- оба сервиса входят в основной путь MVP;
- дубли и потерянные задачи отсутствуют.

Итог сообщи кратко: ссылка на Project, количество созданных/переиспользованных Epic и задач, ссылки на главные Epic, первая очередь Ready, критический путь, неназначенные роли и точные ограничения. Отдели фактически выполненное от подготовленного и недоступного.
