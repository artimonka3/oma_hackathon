# ОМА: каркас Go-приложения и доменных модулей

Реализация этапа «Создать каркас Go-приложения и доменные модули» по
[продуктовой спецификации](../upload/OMA-product-spec.md) и
[техническому приложению](../upload/technical-spec.md).

Критерии выполненного этапа:

- **Приложения собираются и запускают HTTP-серверы** — три процесса:
  `cmd/app` (основной API, :8080), `cmd/mockoma` (симулятор магазина, :8090),
  `cmd/worker` (обработка заданий, health на :8081).
- **Модули имеют явные границы; бизнес-логика не находится в обработчиках** —
  домены `internal/project`, `internal/soberi`, `internal/prorab` владеют
  правилами; обработчики `internal/httpapi` только парсят запрос, вызывают
  сервис и пишут ответ. Переходы состояний, проверка прав, версионирование
  и расчёты живут в доменах и покрыты unit-тестами.
- **Описан минимальный запуск без реального API ОМА** — см. раздел ниже.

## Минимальный запуск (без реального API ОМА)

Вариант 1 — два процесса, интеграция через HTTP (как в промышленной схеме):

```bash
go run ./cmd/mockoma                      # симулятор API магазина на :8090
OMA_API_BASE_URL=http://localhost:8090 \
OMA_APP_BASE_URL=http://localhost:8080 \
go run ./cmd/app                         # основной API на :8080
go run ./cmd/worker                      # обработка заданий, health на :8081
```

Вариант 2 — один процесс, встроенный симулятор магазина:

```bash
go run ./cmd/app   # OMA_API_BASE_URL не задан -> используется oma.Fake
```

Проверка сквозного пути (сборка, запуск, полный сценарий клиента и прораба,
идемпотентность cart-sync, события оплаты, поведение при недоступности магазина):

```bash
./scripts/smoke.sh   # SMOKE OK
```

Только сборка и тесты доменов:

```bash
make build && make test && make vet
```

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `APP_ADDR` | адрес основного API | `:8080` |
| `OMA_API_BASE_URL` | база HTTP API магазина; пусто — встроенный `oma.Fake` | — |
| `OMA_APP_BASE_URL` | адрес основного backend для обратных вызовов mockoma | — |
| `OMA_SERVICE_SECRET` | секрет сервисного клиента (`/internal/v1/oma/*`) | — |
| `MEDIA_STORAGE_PATH` | локальный каталог медиа | `./var/media` |
| `DEMO_MODE` | разрешает демо-сессии и смену ролей | `true` |
| `AI_MODE` | режим AI-провайдера; `demo` — заглушка | `demo` |
| `MOCKOMA_ADDR` / `WORKER_ADDR` | адреса симулятора и worker | `:8090` / `:8081` |

## Структура (раздел 1.2 ТЗ)

```text
cmd/app/                 основной Go-сервер
cmd/mockoma/             симулятор API магазина (отдельный процесс)
cmd/worker/              обработка сохранённых заданий
internal/project/        проекты, помещения, доступ, инвентарь, версии
internal/soberi/         варианты дизайна, спецификация, подготовка корзины
internal/prorab/         проверки, планы, отчёты, решения, приёмка
internal/integrations/oma/ клиент API магазина (HTTP-клиент + встроенный Fake)
internal/ai/             контракт AI-провайдера и валидация черновика
internal/media/          файлы и управление доступом
internal/jobs/           сохранённая очередь заданий и worker
internal/events/         журнал доменных и входящих событий
internal/httpapi/        маршруты, сессии, конверты ошибок (тонкие обработчики)
internal/store/          граница транзакций (InMemoryRunner до PostgreSQL)
internal/mockoma/        домен симулятора магазина
web/                     место браузерного слоя (этап D+)
migrations/               черновик схемы этапа A (PostgreSQL)
fixtures/                демо-товары и демо-профили (признак demo)
```

## Границы модулей

- `httpapi` знает все домены, но домены не знают про HTTP; обработчик
  вызывает один метод сервиса и не содержит условий бизнес-логики.
- `soberi` и `prorab` зависят от `project` (общий агрегат) и от контракта
  `oma.Client` — не друг от друга.
- Магазин общается с backend только по HTTP через `/internal/v1/oma/*`,
  даже при локальном запуске — код не зависит от его внутренней базы.
- Заменяемые интерфейсы: `oma.Client`, `ai.Provider`, `media.Storage`,
  `project.Repository`, `store.Runner` — реальные интеграции подключаются
  без изменения доменного кода.

## Что уже работает в каркасе

- Демо-сессии трёх участников (client / foreman / mediator), только при
  `DEMO_MODE`.
- Проект: создание, PATCH по `expected_version` (409 при конфликте),
  помещения, загрузка медиа, подсказки из истории покупок (status
  `suggested` не влияет на закупку), подтверждение партий.
- Собери: очередь дизайн-заданий с worker'ом, выбор варианта, расчёт
  спецификации по правилам v1 (площадь стен, расход краски, упаковки),
  `cart-sync` с идемпотентностью строк (повтор не удваивает корзину).
- Прораб: preflight (`ready`/`needs_data` с вопросами), адресная карточка
  проверки (повторный запрос не создаёт дубли), решения исполнителя,
  `review_input_hash` и принятие предложенных правок по совпадению
  отпечатка, планы работ, запуск этапов, версии отчётов, приёмка
  (только владелец, только по текущей версии отчёта, только с явным
  `acceptance_confirmed=true`), прогресс приёмки по весам этапов.
- Симулятор: каталог, поиск, история, корзины с версиями, заморозка
  котировки, оформление, серверная авторизация оформления перед оплатой,
  события оплаты/доставки в журнал проекта (дедупликация по event_id).
- Конверт ошибок `{code, message, details, request_id}`: `FORBIDDEN`,
  `NEEDS_DATA`, `VERSION_CONFLICT`, `INVALID_TRANSITION`, `REPORT_CHANGED`,
  `INTEGRATION_UNAVAILABLE`, `NOT_IMPLEMENTED` и др.
- Маршруты следующих этапов (назначения, изменения, обращения, завершение)
  зарегистрированы и честно отвечают `501 NOT_IMPLEMENTED`.

## Сознательные упрощения каркаса

- Хранилища in-memory: перезапуск очищает данные; PostgreSQL и общая
  транзакция «команда + версия + событие» — этап A, интерфейсы готовы.
- Очередь заданий живёт в процессе `app`; `cmd/worker` после этапа A
  подключается к общей очереди на PostgreSQL.
- `review_input_hash` в канонизации v1 учитывает цель, режим и геометрию
  комнат; расширение состава (материалы, имеющееся) — этап F.
- `/internal/v1/oma/checkout-authorizations` фиксирует контракт
  (серверная авторизация обязательна), полная проверка подтверждений —
  этап G.
