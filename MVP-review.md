# ОМА: ревью и кратчайший путь к MVP

Дата: 28 октября 2026. Проверены текущий Go-код, исходники HTML-прототипа и `/Users/artemgolak/OMA-kanban.xlsx`, лист «Задачи».

> Это ревью состояния **до реализации**. После него основной сценарий собран в рабочий MVP: актуальные возможности, запуск и ограничения описаны в [README.md](README.md). Находки ниже сохранены как история исходного состояния.

## Вывод

Начинать заново не нужно. Уже есть адаптивный интерфейс и работающая цепочка API: проект → помещение → варианты → спецификация → корзина → проверка прорабом → план → отчёт → приёмка, а также симулятор заказа. Но это две отдельные реализации: браузерная демонстрация и серверная демонстрация. Сквозного приложения для пользователя пока нет.

Быстрее всего собрать один законченный сценарий: **одна комната, покраска стен, подтверждённые остатки, ручные размеры, комплект материалов, самостоятельная покупка либо подбор прораба из корзины, проверка комплекта, демозаказ, один этап с отчётом и приёмкой**. Два отдельных сервиса в интерфейсе сохраняются. Общими остаются проект, материалы и корзина.

Не нужно переписывать UI на React, выделять микросервисы, строить нативное приложение или реализовывать все задачи Excel перед первой демонстрацией.

## Что фактически есть

| Часть | Состояние | Что требуется для MVP |
|---|---|---|
| Дизайн сайта и телефона | Есть автономный HTML/CSS/JS, два отдельных входа, последовательные вопросы, экраны корзины и ремонта | Подключить к API, сохранить текущий простой UX |
| Состояние интерфейса | `design-prototype/app.js` хранит его в `localStorage`, вызовов `fetch` нет | Сервер хранит проект и решения; браузер хранит только локальный черновик и идентификаторы |
| Go-приложение | Собирается, домены разделены, ошибки и версии существуют | Раздавать UI и API с одного origin, описать минимальный контракт |
| Авторизация | Демо-сессии с Bearer-токенами, часть команд проверяет владельца/исполнителя | Исправить доступ к jobs и медиа; для показа использовать явные демо-роли |
| Проекты и комнаты | Создание, чтение проекта, изменение проекта с `expected_version`, добавление комнат | Доработать восстановление полного состояния, редактирование размеров и при необходимости список проектов |
| Остатки | История → suggested; ручной ввод/подтверждение → confirmed | Количество и пригодность валидировать; confirmed реально учитывать в закупке |
| Варианты дизайна | Очередь и проверка допустимых SKU есть; AI — фиксированная заглушка | Подготовить согласованные комплекты; связать выбранный вариант с расчётом |
| Расчёт материалов | Только упрощённое правило покраски, 0,1 л/м² | Использовать выбранную краску, число слоёв и расход товара, учитывать остатки, округлять упаковки после вычитания |
| Магазин | Встроенный Fake и HTTP Mock OMA; товары, история, версии корзины, котировка, демооплата | Единый каталог с UI, одинаковое поведение адаптеров, серверный доступ к корзине/оформлению из приложения |
| Подбор прораба | Профили, фильтры по специализации и региону | Анализировать именно текущую корзину и объяснять рекомендации |
| Проверка комплекта | Карточка запроса, дедупликация, решения назначенного прораба | Включить состав и остатки в отпечаток, инвалидировать устаревшие решения |
| Назначение исполнителя | Режим проекта есть, но endpoints engagements возвращают 501 | Для MVP сохранить выбранного прораба и явное подтверждение назначения; полный договорной процесс отложить |
| План, отчёт, приёмка | Есть API, версии отчётов, явное решение владельца, взвешенный прогресс | Подключить UI двух ролей, фото и необходимые ограничения старта |
| Изменения, посредник, завершение | Нарисованы; соответствующие серверные endpoints возвращают 501 | Убрать из обещаний первой версии; отдельные этапы после MVP |
| Данные и фоновые задания | Бизнес-данные, сессии, очередь и журнал в памяти; файлы пишутся на диск | Для демо — управляемый reset/seed; для пилота — постоянное хранилище и восстановление после рестарта |
| Отдельный worker | Собственная демонстрационная очередь, задания app выполняются внутри app | Для первой версии оставить обработчик внутри app; отдельный worker пока не запускать как необходимый компонент |

### Важное отличие от UX

В прототипе различаются покраска, пол и плитка. Сервер этого покрытия не обеспечивает: правило расчёта сейчас только про покраску. Поэтому обещать все три направления в первом рабочем релизе нельзя. Неподдерживаемые запросы должны получать понятное ограничение, а не случайный комплект краски.

## Находки ревью

### 1. P1 — оформление разрешается без проверки оснований

`internal/httpapi/handlers_misc.go:29–49`: обработчик checkout-authorizations декодирует запрос и без доменных проверок возвращает `authorized`. При пустом сервисном секрете внутренние маршруты также доступны без него.

**Проверено HTTP:** POST с `{}` вернул 200 и `status: authorized` с пустыми идентификаторами.

**Исправить:** проверять сохранённый контекст оформления, связь котировки/корзины/проекта, сумму, валюту, актуальные версии, подтверждённые размеры и основание покупки. В режиме foreman — актуальную проверку выбранного исполнителя. В режиме self — отдельное подтверждение владельца без обязательного прораба. Сервисный секрет обязателен для опубликованного окружения. Отсутствие callback-конфигурации не должно незаметно означать разрешение оплаты в интегрированном демо.

Задачи: Q01, Q02, M05, F07.

### 2. P1 — расчёт не соответствует выбору и остаткам; адаптеры дают разный результат

`internal/soberi/service.go:191–247`: выбирается самый дешёвый результат поиска `paint`; выбранный дизайн влияет только на текст вопроса. Подтверждённые остатки в расчёт не читаются.

`fixtures/products.json:4`: грунт PRIMER-DEEP имеет категорию `paint` и стоит дешевле краски. Встроенный Fake ищет по категории, HTTP Mock — по названию/SKU через параметр `q`. Поэтому результаты различаются.

**Проверено HTTP во встроенном Fake:** для комнаты 4 × 5 × 2,7 м расчёт выбрал PRIMER-DEEP за 9900 копеек. После добавления подтверждённых 100 л того же SKU сумма осталась 9900. HTTP smoke в отдельном Mock получил другой итог — 18500.

**Исправить:** разделить тип материала/назначение и поисковую строку, выбирать SKU из подтверждённого варианта, хранить технический расход и число слоёв, валидировать единицы. Вычитать только совместимый пригодный confirmed-остаток. Формула: потребность → вычитание доступного остатка → округление закупки вверх до упаковок. При полном покрытии остатком новая закупка равна нулю. Проверить одинаковые результаты Fake/HTTP на одних fixtures.

Задачи: A04, I01, I04, I05, I08, M01, M08.

### 3. P1 — проверка прораба не привязана к материальному составу

`internal/prorab/service.go:162–176`: inputHash включает цель, режим и геометрию, но исключает SKU, количества, подтверждённые остатки и спецификацию. Preflight также не проверяет состав корзины. Замена материала при той же комнате не меняет отпечаток.

Отдельно: при предложении changed_skus хеш строится с добавлением SKU (`:309–316`), а при принятии считается прежней функцией без SKU (`:355–359`). Обычная замена SKU не может таким способом получить совпадающий итоговый отпечаток.

**Исправить:** единый канонический снимок существенных входных данных, версия правил и сравнение при решении прораба и при покупке. На первый MVP достаточно «подтвердить текущий комплект» / «запросить уточнение»; точные предложенные замены можно временно исключить из доступного UX.

Задачи: R04, R06, R07, R08, Q02.

### 4. P1 — результат задания доступен без проверки доступа к проекту

`internal/httpapi/handlers_soberi.go:32–38`: наличие любой сессии достаточно для GET job по ID. Проверки actor → project нет; ответ содержит и вход задания.

**Проверено HTTP:** один и тот же прораб получил 403 на проект клиента и 200 на принадлежащее этому проекту задание.

**Исправить:** после чтения job проверять доступ к job.ProjectID. Для медиа проверять доступ **до записи**: сейчас handleAddCapture сначала сохраняет файл, затем проверяет проект через NoteCapture. Добавить защищённое чтение фото и проверку принадлежности PhotoIDs отчёта проекту; текущий storage имеет только Save, а обработчик отчёта принимает IDs без этой проверки.

Задачи: F07, P03, T04.

### 5. P1 для пилота — после рестарта теряется весь процесс ремонта

`cmd/app/main.go`, `internal/project/service.go`, `internal/store/store.go`: используются map-репозитории, общая транзакция — noop. Миграция существует как черновик, но SQL-репозитории и применение миграций не подключены. Схема не покрывает весь текущий процесс: нужны ещё варианты, спецификации, проверки, планы, отчёты, решения и связи с заказом.

**Решение по сроку:** управляемое одноразовое демо может работать в памяти с seed/reset и явно обозначенной границей. MVP для реальных пользователей должен сохранять состояние на диск через БД и выдерживать рестарт. Нельзя назвать наличие SQL-файла подключённой PostgreSQL.

Задачи: F03, F08, T01.

### 6. P2 — недостаточно проверок выполнения и конкурентных операций

StartStage проверяет подтверждение плана и назначенного прораба, но не зависимости этапов/готовность материалов. CreateWorkPlan сохраняет план до проверки всех этапов: ошибка в позднем элементе оставляет частичный план. SessionStore использует обычную map без синхронизации между HTTP-запросами.

**Исправить:** валидировать весь план до записи, сохранять команду атомарно, защитить session map. Для покраски явно определить материальные условия каждого этапа: нельзя универсально требовать доставку всей корзины, если подготовительные работы допустимы раньше. Добавить адресные тесты этих случаев: существующий `-race` не покрывает конкурентную работу HTTP-сессий.

Задачи: E01, E03, F07, F08, T03, T04.

## Конкретный порядок реализации

Оценка — предварительная, для двух участников, знакомых с проектом: один Go, один frontend. Это не обещание срока. Для связанного хакатонного демо закладывать примерно **6–10 человеко-дней / 3–5 рабочих дней вдвоём**, с риском увеличения после согласования API. Постоянное хранение и доведение до пилота оценивать отдельно; ориентир ещё **3–6 человеко-дней** для выбранного узкого сценария, не для всего ТЗ.

| Пакет | Кто | Результат и критерий готовности |
|---|---|---|
| 0. Зафиксировать сценарий и данные | Вместе, 0,5 чел.-дня | Одна комната/покраска; общие SKU, единицы, цены и профили; два сервиса с отдельными входами; убрать недоступные действия |
| 1. Серверный расчёт и решения | Go, 1,5–2,5 чел.-дня | Выбор варианта определяет SKU, confirmed-остаток уменьшает закупку, новый состав отменяет старую проверку; закрыты находки 1–4 |
| 2. Подключить «Собери» | Frontend + небольшой API-слой Go, 1,5–2,5 чел.-дня | Бриф → остатки → пропустить скан/размеры → варианты → серверная спецификация → серверная корзина; после F5 восстанавливается состояние |
| 3. Подключить «Прораб» | Go + frontend, 1,5–2,5 чел.-дня | Вход из корзины, серверный анализ категорий, подходящие специалисты, сохранённый выбор, запрос проверки и ответ в кабинете выбранной демо-роли |
| 4. Заказ и приёмка | Go + frontend, 0,5–1 чел.-дня | Котировка → серверное разрешение → демооплата; заказ виден в UI; план, фотоотчёт и явная приёмка одного этапа |
| 5. Надёжный показ | Вместе, 0,5–1 чел.-дня | Один запуск, health polling, seed/reset, HTTPS, прогон телефона и двух ролей, отсутствие ошибок и ложных успешных состояний |

Пакеты 1 и 2 можно делать параллельно после фиксации общего DTO. Пакеты 3–4 зависят от серверного комплекта и согласованного контракта. Если до защиты меньше суток, целиться в путь до корзины и запроса проверки; заказ/ремонт обозначить следующей итерацией, не выдавать автономные экранные переходы за работающий backend.

### Минимальный технический способ соединения

1. Источник UI — `design-prototype/index.html`, `app.js`, `styles.css`, assets. Большой `oma-prototype.html` оставить артефактом презентации, не основной точкой разработки.
2. Go раздаёт статику и `/api/v1` с одного origin. Mock OMA доступен приложению как серверная интеграция; браузеру не нужны прямые обращения к отдельному порту магазина.
3. Небольшой `api.js`: запросы с Bearer demo-session, обработка 409/422/503, состояния ожидания/ошибки, опрос фонового job. Не считать команду успешной до ответа сервера.
4. Использовать имеющиеся project/room/inventory/design/cart-sync/review/plan/report/decision endpoints. Добавить чтение последних вариантов/выбора/спецификации/корзины/заказа для восстановления UI. Текущий GET проекта возвращает проект, комнаты и next_actions, а не весь экранный процесс.
5. Добавить прикладные endpoints для анализа корзины, выбранного исполнителя и checkout. Расширить OmaClient чтением корзины, котировкой и заказом: сейчас контракт содержит только поиск товара, карточку, историю и SyncCart. Не отдавать сервисный секрет в JS.
6. В браузере убрать второй независимый расчёт закупки и статусов. Форматирование остаётся на frontend, деньги, количества, версии и разрешения — на Go.
7. Фото необязательно для подбора; подтверждённые реальные размеры обязательны перед окончательной закупкой. Сканирование можно пропустить, ручной ввод не должен зависеть от AR.
8. Для демо оставить подготовленные визуальные референсы и честно помеченный AI demo. Если жюри требует живую модель, отдельно подключить один структурированный вызов для брифа/варианта с timeout, проверкой SKU и demo-fallback. Модель не считает деньги и не принимает ремонт.

### Следующий пакет для пилота

PostgreSQL и миграции всех используемых сущностей, транзакции команда+версия+событие, восстановление jobs, повторная доставка событий магазина с тем же event_id, защищённое чтение медиа, реальные пользовательские сессии вместо общих демо-аккаунтов. После этого проверка рестарта app/магазина и повторов команд. Время этого пакета нельзя заменять отметкой «схема БД уже есть».

## Критерии приёмки MVP

- Сайт открывается на компьютере и телефоне; стартует вопросом «Не знаете, что вам нужно?».
- Описание комнаты и задачи сохраняется на сервере; неподдерживаемые работы обозначаются явно.
- Без остатков, с suggested и с confirmed получаются корректно разные расчёты; неподтверждённое наличие не уменьшает покупку.
- Скан можно пропустить. До покупки доступны ручные размеры и подтверждение пересчёта.
- Выбор другого комплекта меняет товары/расчёт; новая версия отменяет прежнее разрешение прораба.
- Корзина едина между сервисами. Пустая корзина не порождает выдуманный подбор прораба.
- Можно остаться в самостоятельном режиме либо перейти отдельной кнопкой в «ОМА.Прораб».
- Отвечает выбранный исполнитель; чужая роль не читает закрытые задания/фото и не принимает этап.
- Нельзя оформить комплект с неподтверждёнными входными данными или устаревшей проверкой. Повтор оплаты одного checkout не создаёт вторую покупку.
- Один этап проходит план → отчёт → замечание/исправление → явная приёмка заказчика. Процент растёт по принятому объёму.
- F5 восстанавливает серверное состояние, ошибка магазина отображается как ошибка, все демонстрационные данные подписаны.
- Для пилота дополнительно: перезапуск backend не теряет проект, материалы, решения, заказ и отчёты.

## Что проверено запуском

- `go test ./...` — проходит.
- `go vet ./...` — проходит.
- `go test -race ./...` — проходит в рамках существующего покрытия. HTTP API, soberi и mockoma не имеют отдельных package-тестов.
- Обычный `bash scripts/smoke.sh` — два неудачных запуска на этапе старта процессов. С временным увеличением всех `sleep` до 5 секунд, **без изменения исходного скрипта**, сценарий прошёл целиком: корзина без дублирования строк, решение прораба, план/отчёт/приёмка, демооплата, входящее событие, 503 при недоступном магазине. Это подтверждает демонстрационный API-путь, но не исправность всех бизнес-правил.
- В smoke стоит заменить фиксированные sleep опросом готовности с timeout; `mkdir -p var` перенести до перенаправления логов; отрицательные проверки включить до заявления о готовности MVP. Текущий smoke даже выполняет отчёт и приёмку до оформления заказа — ограничения готовности материалов им не проверяются.
- Изолированные HTTP-проверки воспроизвели выбор грунта в Fake, отсутствие вычитания confirmed-остатка, доступ к чужому job и разрешение пустой авторизации оформления.
